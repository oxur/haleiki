## What Worked

- **Spiking the `pagefind` crate's source before writing any indexing code** (per the cc-prompt's explicit first-task instruction) surfaced two load-bearing facts that would otherwise have caused real bugs: (1) `add_custom_record`'s `content` is indexed and excerpted **verbatim** — no HTML parsing happens for the custom-record path (confirmed by reading `Fossicker::fossick_sync`: the `data.is_none()` guard skips `fossick_html_sync` whenever `new_with_data` was used to construct the `Fossicker`) — which is *why* `markdown_to_plain_text` exists at all, rather than passing raw Markdown/HTML straight through. (2) The WASM binary's real on-disk name is `wasm.{lang}.pagefind` (extension `.pagefind`, confirmed against a real build **and** the crate's own `service::api` test), not the `.wasm` the slice-doc assumed sight-unseen — caught and corrected in `pagefind_content_type_for` before it became a silent 404 in a browser.
- **Running two independent `haleiki export` invocations by hand** before trusting the pre-existing determinism test caught a real, upstream, non-Haleiki issue early: `pagefind` 1.5.2's own `src/index/mod.rs` carries a `// TODO: Change filter indexes to BTree to give them a stable hash` — its filter-value HashMap iterates in a per-process-random order, so 2 of ~330 bundle files differ byte-for-byte across separate process runs. Diagnosed by diffing two real export trees rather than guessing from the failure message, scoped the fix precisely (exclude `pagefind/` from the byte-for-byte comparison, not weaken the guarantee for the ~327 unaffected files), and documented the upstream root cause in the test itself so it doesn't read as a Haleiki regression to a future reader.
- **Composing pagefind-serving alongside `handle`/`resolve` rather than folding it into them** (`handle_request` is a new, separate function; neither `handle`'s nor `resolve`'s signature or behavior changed) meant all ~30 of Arc 03's existing, CDC-verified tests kept passing completely unmodified — the slice-doc's "do not change resolve's existing routing semantics" boundary held by construction, not by care taken while editing shared code.
- Two test-only bugs (a self-referential `include_str!` needle catching this file's own "npx" doc-comment prose; a `sort_unstable()`-on-urls comparison that silently used a different sort key than `build_records`'s actual sorted-by-slug walk, for the `language`/`language-family` prefix pair) were both caught by the test suite itself failing honestly — confirming, again, that this project's `include_str!`-self-reference lesson and "assert against independently-derived expected values, not a re-derivation of the same computation" discipline are both still earning their keep.
