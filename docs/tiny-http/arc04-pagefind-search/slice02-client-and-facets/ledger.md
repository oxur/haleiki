## What Worked

- **Spiking Pagefind's actual filter-query behavior against the real bundle before writing `search.js`'s facet logic** (mirroring the "spike first" discipline slice 01 established for the crate's record API) caught a real, load-bearing wrong assumption: the slice-doc's proposed within-group OR (`{category:["a","b"]}`) is actually Pagefind's AND shape; the correct OR form (`{any:[...]}`) was found via Pagefind's own docs plus an empirical 2-value-array-returns-0-results test against the live bundle. Writing the facet reducer against the *wrong* assumption first, then correcting it once, was far cheaper than finding this bug via a flaky-looking "facet toggle does nothing" symptom later.
- **The headless-browser harness caught a real DOM bug within its first run** that no amount of code review would likely have found: `search.js` assumed `.search-results-list`/`.search-status`/`.search-results-count` always exist in the initial DOM (just hidden/shown), but `render_search`'s shell (Arc 02, untouched by this slice) only ever server-renders the `.search-empty` branch — those three elements are *never* present pre-hydration. Every e2e step touching real results timed out identically until this was diagnosed (via a raw Playwright script with `page.on('pageerror')` wired up, then direct DOM-state inspection) and fixed with a get-or-create pattern. This is exactly the kind of defect the ledger's decision to require a *real* browser (not a Rust-side mock) was chosen to catch.
- **Verifying "no-match" empirically rather than assuming any nonsense string works** avoided a second, subtler false test: Pagefind's fuzzy/partial-credit matching returned non-zero results for every plausible-looking ASCII gibberish string tried (long repeated letters, keyboard-mashing, a 20-digit number) — a CJK string with zero character overlap with the corpus was the first query that reliably returned zero, found by spiking several candidates directly against the real index rather than guessing.
