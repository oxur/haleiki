## What Worked

- Reading the `tiny_http` crate's own crate-level docs before writing `server.rs` de-risked the concurrency design up front: the "N worker threads each calling `recv()` on a shared `Arc<Server>`" pattern this slice needed is literally the crate's documented idiom, not a novel design under test.
- Keeping `resolve()` fully pure (no socket, no request/response types in its signature) meant the bulk of F-3/F-4/F-5/F-7 verification could live in fast, deterministic unit tests against the real demo corpus and real on-disk asset files, with exactly one live-server test needed for F-6 — matching the cc-prompt's explicit guidance to keep verification weight on the pure router.
- Hand-checking real repo asset files (`ls assets/...`) before writing content-type assertions caught that there's no real `.svg` or `.json` file in the repo (macros.jinja inlines SVG), so those two extensions are covered by a separate pure `content_type_for` unit test rather than an end-to-end `resolve` call against a nonexistent file.
- Binding a raw `Server::http("127.0.0.1:0")` directly in the live-smoke test (rather than calling the blocking `serve()` wrapper) avoided needing any graceful-shutdown machinery — explicitly out of scope for this slice — while still exercising the real `recv()`/`resolve()`/`respond()` path over a real socket.
