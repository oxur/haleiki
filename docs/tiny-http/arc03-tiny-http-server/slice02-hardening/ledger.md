## What Worked

- Reading `tiny_http`'s `respond_impl` source before designing `handle`/HEAD paid off directly: it revealed that `tiny_http` already suppresses the body write for any `Method::Head` request regardless of what response is handed to `respond()` (`do_not_send_body = self.method == Method::Head`, checked against the *original request*, not the response object). That meant the belt-and-suspenders design — `handle()` also explicitly empties the body and states a matching `content_length` for `HEAD` — is safe on both layers: even a bug in `handle()` couldn't leak body bytes over a real `HEAD` request, and the pure function is still independently, exactly unit-testable without a socket.
- Tracing through `Response::add_header`/`raw_print` before writing the `nosniff`/`Content-Length` unit test caught a wrong assumption early: an explicitly-set `Content-Length` header is *not* stored in `response.headers()` — `tiny_http` intercepts it into an internal `data_length` field and only re-adds it as a real header at `raw_print` time. Checked via `response.data_length()` instead once found; a live `curl -sD -` check independently confirmed the header actually appears on the wire.
- Keeping the deliberate-panic trigger for the panic-isolation live test entirely inside the test's own closure (a magic path string the *test* recognizes, not a branch in `server.rs`) avoided ever putting a "make me panic" backdoor in production code, while still exercising the real `guarded`/`handle`/`build_response` functions end-to-end over a real socket.
